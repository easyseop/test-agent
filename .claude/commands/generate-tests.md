(인자 형식: `<앱이름> [계획 파일] [소스 경로] [설명서 경로…]`
 — 인자가 없으면 무엇을 대상으로 할지 먼저 물어라)

## 왜 이렇게 바꿨나 (2026-08-11)

**어디서 가져왔나.** Playwright Test Agents의 Generator를 본떴다.
(`packages/playwright/src/agents/playwright-test-generator.agent.md`)

**바꾸기 전 문제.** 이 명령은 `discovery.json`(정지된 스냅샷)과 소스코드만 보고
설정을 썼다. 그래서 셀렉터가 맞는지는 **다 쓰고 실행해봐야** 알았고, 틀리면
고치고 다시 돌리기를 반복했다. 확인 단계가 절차에 없었다.

**원본에서 가져온 한 줄이 이것이다.**

> *"각 단계와 검증마다: Playwright 도구로 실시간으로 직접 실행해 보라"*

코드를 상상해서 쓰지 말고 **실제로 눌러보며 확정하라**는 것이다. 원본이 뽑는
셀렉터가 잘 안 깨지는 이유가 이 한 줄이다.

**우리는 그걸 우리 도구로 한다.** 브라우저를 AI가 직접 몰면 화면마다 토큰이
나가는데, 우리에겐 같은 일을 하면서 토큰을 안 쓰는 명령이 이미 있다.

| 원본 | 우리 | 토큰 |
|---|---|---|
| AI가 브라우저를 몬다 | `discover`가 한 번에 훑는다 | 0 |
| AI가 응답을 눈으로 읽는다 | `inspect-api`가 구조를 뽑는다 | 0 |
| 단계마다 실행해 확인한다 | `check-config`가 한 번에 확인한다 | 0 |

**셀렉터 고르는 기준도 가져왔다.** 원본은 자리 기반(`div > section > button`)
대신 역할·글자 기반을 쓴다. 실측 결과는 아래 §셀렉터 규칙에 있다.

**Healer는 가져오지 않았다.** 실행 중에 셀렉터를 바꿔치기하므로, 버튼이 진짜
사라진 결함까지 덮는다.

## 절차

### 1. 기대값의 근거를 확보한다

**채워진 계획 파일**(`/plan-tests` 결과)이 있으면 그것을 쓴다. 빈칸이 남아
있으면 **그 항목은 만들지 않는다.** 빈칸 목록을 보고하고 멈춰라.

계획 파일이 없으면 설명서(README·기획 문서)를 읽고 각 기능의 **의도된 동작**
("~하면 ~만 표시된다")을 목록화한다.

⚠️ **기대값은 여기서만 나온다.** 구현 코드의 조건문을 베끼면 구현 버그가
기대값에 복제되어 그 검사는 영원히 통과한다. 소스코드는 셀렉터·라우트·
테이블명 등 **좌표 확인 용도로만** 본다.

### 2. 화면을 실제로 확인한다 (상상해서 쓰지 않는다)

```bash
python3 -m webtest_agent discover -c <설정>
```

표의 셀렉터·헤더·**행 수**가 나온다. 행 수를 반드시 본다 — 1행짜리 표를
정답원과 대조해봐야 증명되는 것이 거의 없고, 그 사실은 설정을 **쓰기 전에**
알아야 한다.

정답원이 API면 응답 구조도 뽑는다.

```bash
python3 -m webtest_agent inspect-api <경로> -c <설정>
```

**실패하면 거기서 멈추고 보고하라.** 화면을 못 본 채로 셀렉터를 지어내면 안 된다.

### 3. `configs/<앱이름>.yaml`을 쓴다

`configs/demo.yaml`을 형식 참고. 문법은 `QUICKSTART.md` §2-2, 전체 순서는
`docs/04-config-walkthrough.md`에 있다.

- 의도된 동작 하나당 검사 하나
- `query`의 조건은 **1번의 근거**에서 도출한다 (구현 쿼리 번역 금지)
- SELECT 컬럼 순서는 `ui_table.columns`와 1:1 대응
- 파괴적 기능(삭제·결제 등)은 시나리오로 만들지 않는다

### 4. 돌리기 전에 확인한다 ← **이 단계가 새로 생겼다**

```bash
python3 -m webtest_agent check-config -c configs/<앱이름>.yaml
```

**'못 찾음'이 0이 될 때까지 고친다.** 이것이 원본의 "실시간으로 실행해 보라"에
해당하는 단계다.

- **못 찾음** — 앞이 다 성공한 상태에서 0개. 고쳐야 한다.
- **확인 못 함** — 앞이 막혀 판단 불가. 앞의 '못 찾음'부터 고치면 대개 풀린다.

`ui_table.columns`가 화면 헤더에 없으면 여기서 잡힌다. 로케일 때문에 열 이름이
다른 경우가 흔하다.

### 5. 한 번 실행해 본다

```bash
python3 -m webtest_agent run -c configs/<앱이름>.yaml
```

**결과가 '실패'여도 그대로 보고한다.** 통과시키려고 기대값을 바꾸지 마라 —
그 순간 이 테스트는 아무것도 증명하지 않게 된다. 실패했으면 셋 중 무엇인지
분류해 보고하라.

| 무엇 | 어떻게 아나 |
|---|---|
| 제품 결함 | 기대값의 근거가 맞고 화면이 다르다 |
| 테스트 결함 | 내가 근거를 잘못 옮겼다 |
| 환경 문제 | 종료코드 2 · `summary.not_proven` > 0 |

### 6. 사람에게 넘긴다

생성·변경한 파일과 **각 시나리오의 근거(설명서 어느 문구)** 를 요약해 보고하라.
특히 `query`의 조건을 검토받아라. 커밋은 사용자 확인 후에.

## 셀렉터 규칙 (실측 근거)

같은 버튼을 가리키는 방식을 바꿔가며 흔한 화면 변경 3가지를 준 결과다.

| 변경 | `#id` | `.class` | 자리 기반 | **역할+이름** |
|---|---|---|---|---|
| id를 바꿈 | ✗ 깨짐 | ✓ | ✓ | **✓** |
| 감싸는 div가 늘어남 | ✓ | ✓ | ✗ 깨짐 | **✓** |
| css 클래스를 바꿈 | ✓ | ✗ 깨짐 | ✓ | **✓** |

**우선순위**

1. `data-testid` 등 테스트용 속성 — 이 목적으로 붙은 것이라 제일 안전
2. **역할+이름** — `role=button[name='조회']` (우리 엔진에서 그대로 동작한다)
3. `#id` — 있으면 쓴다. 다만 개발자가 자주 바꾼다
4. 자리 기반(`div > section > button`) — **최후 수단.** 구조가 조금만 바뀌어도 깨진다

**역할+이름의 약점도 알고 써라.** 버튼 글자가 바뀌거나(저장 → 등록) 화면 언어가
바뀌면 깨진다. 다만 그 경우는 **깨지는 게 맞다** — 사람이 봐야 할 변화다.
언어는 `target.locale`로 맞춘다.

## 금지

- **근거 없는 기대값을 지어내지 마라.** 근거가 없으면 시나리오를 만들지 말고
  "설명서에 이 기능의 의도가 없다"고 보고하라.
- **화면을 확인하지 않고 셀렉터를 쓰지 마라.** 2·4단계를 건너뛰지 마라.
- **통과시키려고 기대값을 바꾸지 마라.**
- **판정 로직(엔진 코드) 수정으로 문제를 우회하지 마라.**
