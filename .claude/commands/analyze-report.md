테스트 실행 결과를 분석하라. 인자: $ARGUMENTS
(인자가 없으면 `runs/` 아래 가장 최근 실행의 `report.json`을 대상으로 한다)

## 절차

1. `report.json`을 읽고 실패/경고 시나리오를 추린다. 각 실패의 `reasons`, `data_check`(누락/초과 행 샘플), `console_errors`, `http_failures`, 스텝별 스크린샷 경로를 파악한다. 스크린샷은 직접 열어 확인한다 (`runs/<실행>/screenshots/…`).
2. **원인 유형을 분류한다**:
   - **앱 버그** — 화면·데이터가 설명서의 의도와 다름 (예: 필터 과포함, 경계 누락, JS 예외)
   - **테스트 결함** — 기대 쿼리·셀렉터·스텝이 잘못됨 (설명서를 다시 읽고 판단)
   - **환경 문제** — 앱 미기동, DB 미시드, 타이밍(대기 부족)
3. 앱 버그로 판단되면 **대상 앱 소스에서 원인 코드를 특정**하고(파일:라인) 수정 방향을 제안한다. 테스트 결함이면 YAML 수정안을 제시한다. 환경 문제면 재현 절차를 안내한다.
4. **knowledge 위키 반영** (CLAUDE.md 규약 준수):
   - `log.md`에 `run` 항목 append (실행 ID, 통과/경고/실패 수, 한 줄 요약)
   - **상태 변화가 있을 때만**: 새 실패 → `apps/<앱>/issues/<슬러그>.md` 생성(증상·원인·재현 시나리오명·증적 경로·상태), 기존 실패 복구 → 해당 이슈 페이지에 해소 기록. `index.md` 갱신.
5. **보고**: 실패별로 "증상 → 원인(유형) → 제안"을 요약한다. 사람이 스크린샷·비디오·트레이스로 직접 확인할 수 있게 경로를 함께 적는다 (트레이스는 trace.playwright.dev에서 열람).

## 금지

- 판정을 뒤집지 마라 — 엔진의 판정이 정답이다. "이 정도는 통과로 봐도 된다"는 분석이 아니라 회귀다.
- 테스트를 통과시키기 위해 기대 쿼리를 구현 코드에 맞춰 고치지 마라. 기대값의 근거는 항상 설명서다. 설명서와 구현이 다르면 그것이 곧 버그 보고 대상이다.
