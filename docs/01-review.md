# 웹 애플리케이션 자동 테스트 에이전트 — 사전 검토 (Phase 1)

> 작성일: 2026-07-23 · 상태: 검토 단계 (설계/구현 착수 전)
> 진행 순서: **검토(본 문서) → 설계 → 구현**

## 1. 요구사항 정리

사용자가 원하는 것:

| # | 요구사항 | 비고 |
|---|---------|------|
| R1 | 대상 앱의 소스코드/레포/설명서와 사용 목적을 입력으로 받아, 존재하는 기능을 파악 | "무엇을 테스트할지 스스로 발굴" |
| R2 | 각 버튼별로 동작을 잘하는지 자동 검증 | UI 인터랙션 테스트 |
| R3 | 필터를 걸어 조회했을 때 화면에 맞는 데이터가 나오는지 + **실제 쿼리 결과와 일치하는지** 검증 | UI ↔ DB 정합성 검증 |
| R4 | 수많은 테스트를 스스로 수행 | 자율성 (프로그램/게이트/에이전트) |
| R5 | 테스트 내용을 파일로 정리, 화면은 녹화(최소 캡처본)하여 테스트 사용자에게 전달 | 증적 + 리포트 |
| R6 | 언어는 Python 위주 | 기술 제약 |
| R7 | 첫 대상은 웹 애플리케이션 (데이터파이프라인/앱 등은 추후) | 범위 |

## 2. 결론 요약

**전체적으로 실현 가능하다.** 다만 구성요소별로 난이도 편차가 크고, 한 가지 근본 난제(오라클 문제, §3.1)에 대한 설계 결정이 품질을 좌우한다.

| 구성요소 | 실현성 | 난이도 | 핵심 기술 |
|---------|--------|--------|----------|
| 브라우저 자동 조작 (버튼 클릭, 필터 입력) | 높음 | 낮음 | Playwright (Python) |
| 화면 녹화(webm) · 스크린샷 캡처 | 높음 | 낮음 | Playwright 내장 기능 |
| UI 표시 데이터 ↔ DB 쿼리 결과 대조 (R3) | 높음 | 중간 | DB 드라이버 + 정규화/비교 로직 |
| 테스트 대상 "스스로 발굴" (R1, R4) | 조건부 | 높음 | 크롤러(결정적) + 선택적 LLM(탐색적) |
| 리포트 생성 (HTML/MD/JSON) 및 전달 | 높음 | 낮음 | 자체 생성 (Jinja 불필요 수준) |

**가장 가치 있는 차별점은 R3(UI↔DB 정합성)이다.** 일반 UI 테스트 도구(단순 클릭/스모크 테스트)는 흔하지만, "화면의 데이터가 DB 기준으로 맞는가"를 자동 대조하는 도구는 기성품이 거의 없다. 반면 이 검증은 정답(오라클)이 명확해서 자동화 신뢰도가 높다.

## 3. 핵심 쟁점 검토

### 3.1 오라클 문제 — "잘 동작한다"를 기계가 어떻게 판정하는가

자동 테스트의 근본 난제. 판정 가능 범위를 정직하게 구분해야 한다.

**기계가 스스로 판정할 수 있는 것** (명세 없이 가능):
- JS 콘솔 에러 / 페이지 크래시 / 처리되지 않은 예외
- 클릭·전환 시 발생하는 HTTP 4xx/5xx 응답, 깨진 링크
- 무반응 버튼 (클릭해도 URL/DOM에 아무 변화 없음 → 경고)
- 무한 로딩, 타임아웃

**기계가 스스로 판정할 수 없는 것** (명세 또는 사람/LLM 판단 필요):
- "기획 의도대로" 동작하는가 (예: 저장 버튼이 저장 후 목록으로 이동해야 하는지, 모달을 닫아야 하는지)
- 시각적 이상 (레이아웃 깨짐 등 — 별도의 시각 회귀 기법 필요, v1 범위 밖 권장)

**예외 — 필터/조회 검증(R3)은 오라클이 명확하다.** "필터 X를 걸면 DB에서 조건 X로 조회한 결과와 같아야 한다"는 명세가 자명하므로, 이 부분은 높은 신뢰도로 완전 자동화할 수 있다. → v1의 중심 기능으로 삼을 것을 권장.

### 3.2 데이터 정합성 검증(R3)의 함정 3가지

1. **기대 쿼리를 누가 정의하는가**
   - (a) **사람이 설정 파일에 작성** — 독립적인 정답이므로 신뢰도 최상. 권장 기본값.
   - (b) 앱 소스코드에서 쿼리를 추출해 그대로 사용 — **동어반복(tautology) 함정**: 구현에 버그가 있으면 기대값에도 같은 버그가 복제되어 영원히 통과한다. 지양.
   - (c) LLM이 코드/문서를 읽고 기대 쿼리를 생성 + 사람이 승인 — 자동화와 신뢰의 절충.
2. **표현 정규화** — UI는 `12,300원`, DB는 `12300`; 날짜 포맷 차이; 정렬 순서 차이. 비교 전 정규화 계층이 필수.
3. **페이지네이션** — UI는 한 페이지 20행만 보여주는데 DB 결과는 500행일 수 있음. 페이지 순회 또는 LIMIT 대응 필요. (v1은 "단일 페이지 + 표시 건수/전체 건수 비교"로 시작 가능)

### 3.3 안전성 (파괴적 액션)

버튼을 무차별 클릭하는 스윕은 위험하다: 삭제/결제/메일 발송/로그아웃 버튼도 클릭해버린다.

- **차단 목록(avoid patterns)**: `삭제|delete|remove|결제|pay|발송|send|logout` 등 텍스트/선택자 기반 스킵 — 필수 기본 탑재.
- **실행 환경 원칙**: 반드시 테스트/스테이징 환경 + 시딩(재생성 가능한) DB에서 실행. 운영 DB는 read-only 계정으로 조회 검증만.
- confirm 다이얼로그는 기본 "취소"로 자동 응답.

### 3.4 실행 환경 전제조건

에이전트가 돌려면 다음이 갖춰져야 한다 (설계 시 확정 필요):
- 대상 앱을 띄울 수 있는 URL (로컬 실행 또는 스테이징)
- DB 접근 자격 (R3 검증용; 최소 read-only)
- 로그인이 있다면 테스트 계정 및 인증 시나리오
- 재현 가능한 테스트 데이터 (시드 스크립트가 이상적)

### 3.5 LLM 도입 여부 — 없어도 되고, 있으면 더 "에이전트"다워진다

- **LLM 없이 (룰 기반)**: 크롤링으로 페이지/버튼/폼 인벤토리 → 버튼 스윕 → 설정 파일 기반 데이터 검증. 결정적이고 비용 0, CI에 바로 적합. **v1로 충분히 유용.**
- **LLM 추가 시**: (1) 소스코드/문서를 읽고 테스트 시나리오를 제안 (R1의 "스스로 파악" 실현), (2) 실패 결과를 사람이 읽기 좋게 원인 요약. 
- **원칙 권장: "제안은 LLM, 판정은 결정적 코드".** 합격/불합격 판정 자체를 LLM에 맡기면 비결정성·비용·환각 리스크가 검증 신뢰도를 훼손한다. LLM은 시나리오 생성과 리포트 요약까지만.
- 비용 참고: 시나리오 제안 1회당 수천~수만 토큰 수준 (모델·앱 규모에 따라 다름). 실행 자체는 LLM 무관이므로 반복 실행 비용은 0.

### 3.6 안정성 (flaky 테스트)

동적 렌더링(SPA) 대기 문제로 간헐 실패가 나기 쉽다. Playwright의 자동 대기(auto-wait) + 명시적 `wait_for` 스텝 + 네트워크 안정화 대기로 대부분 완화 가능. 설계 시 "스텝 DSL에 대기 액션 포함"으로 반영.

## 4. 기성 도구 지형 — 왜 직접 만드는가

| 도구 | 제공하는 것 | 부족한 것 |
|------|-----------|----------|
| Playwright (Python) | 브라우저 자동화, 자동 대기, **비디오 녹화/스크린샷/트레이스 내장** | 테스트 발굴·판정·리포트는 직접 구현해야 |
| pytest + pytest-playwright | 시나리오를 코드로 작성하는 테스트 프레임워크 | "스스로 발굴" 없음, DB 대조 없음 |
| 상용/OSS QA 에이전트류 (LLM 탐색 테스트 도구) | 자율 탐색 클릭 | **UI↔DB 정합성 검증 없음**, 한국어 리포트/커스텀 어려움 |
| Allure, pytest-html | 리포트 뷰 | 나머지 전부 |

→ **결론: Playwright를 기반 엔진으로 쓰고, 그 위에 (1) 인벤토리 크롤러, (2) 버튼 스윕, (3) UI↔DB 정합성 오라클, (4) 증적 수집·한국어 리포트를 직접 구축하는 것이 합리적.** 바퀴의 재발명은 브라우저 제어(이미 해결됨)가 아니라, 우리 요구 특화 계층에만 투자한다.

## 5. 제안 아키텍처 방향 (설계 단계에서 상세화)

```
[대상 앱 URL + 설정(YAML) (+ 소스/문서)]
        │
        ▼
 ① Discover  페이지 크롤링, 버튼/링크/폼/필터 인벤토리 작성
        ▼
 ② Plan      룰 기반 시나리오 생성(버튼 스윕) + 설정된 데이터 검증 시나리오
        │      (선택) LLM이 코드/문서 기반 추가 시나리오 제안
        ▼
 ③ Execute   Playwright로 실행 — 시나리오별 비디오 녹화, 스텝별 스크린샷,
        │      콘솔 에러/네트워크 실패/다이얼로그 수집
        ▼
 ④ Verify    자동 신호 판정(에러/무반응/HTTP 실패)
        │      + UI 테이블 추출 ↔ DB 쿼리 실행 결과 대조(정규화 후 비교)
        ▼
 ⑤ Report    HTML(스크린샷 내장, 단일 파일) + Markdown + JSON
              + 시나리오별 webm 비디오 → 테스트 사용자에게 전달
```

- 검증 엔진(④)과 실행 드라이버(③)를 분리해두면, 추후 웹이 아닌 대상(API, 데이터파이프라인)도 드라이버만 교체해 확장 가능 — R7의 "웹 먼저, 나중에 확장" 요구와 부합.
- 데모용 샘플 웹앱(Flask + SQLite, **의도적 버그 주입 모드** 포함)을 함께 만들어, "에이전트가 실제로 버그를 잡아내는" 엔드투엔드 검증을 처음부터 가능하게 한다.

## 6. 단계별 로드맵 제안

| 단계 | 내용 | 판단 |
|------|------|------|
| Phase 1 | 검토 (본 문서) | ✅ |
| Phase 2 | 설계 — 모듈 구조, 설정 스키마(YAML), 시나리오 DSL, 비교 규칙, 리포트 형식 | 다음 |
| Phase 3 (v1) | 구현 — 데모앱 + 크롤러 + 버튼 스윕 + config 기반 UI↔DB 검증 + 비디오/스크린샷 + HTML/MD 리포트 | LLM 없이 완결 |

## 7. 설계 착수 전 결정이 필요한 사항

1. **첫 검증 대상**: 동봉 데모앱으로 시작할지, 실제 보유한 앱(URL/DB 정보 필요)부터 겨냥할지
2. **기대 쿼리 정의 방식**: 사람이 YAML로 작성 / LLM 생성 후 사람 승인 / 완전 자동
3. **LLM 기능 포함 여부**: v1부터 하이브리드로 넣을지, 순수 룰 기반으로 시작할지
4. **인증**: 대상 앱에 로그인이 있는지, 테스트 계정 제공 가능한지
5. **리포트 전달 채널**: 파일 산출로 충분한지, 추가 전달(메일/슬랙 등)이 필요한지
