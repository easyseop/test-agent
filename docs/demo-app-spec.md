# 주문 관리 대시보드 — 기능 설명서 (기획 의도)

> 이 문서는 **제품이 어떻게 동작해야 하는가**를 적은 기획 문서다.
> 구현 코드가 아니라 이 문서가 테스트 기대값의 **유일한 근거**다.
> 구현이 이 문서와 다르게 동작하면 **구현이 틀린 것**이다.
>
> 작성 원칙: SQL·함수명·파일경로를 쓰지 않는다. 업무 용어로만 적는다.

## 1. 이 화면은 무엇인가

주문 담당자가 **주문 목록을 조건별로 좁혀 보고, 그 결과가 실제 데이터와 맞는지
확인**하는 대시보드다. 조회 전용이며, 이 화면에서 주문을 고치거나 지우지 않는다.

주문 하나는 다음 정보를 가진다: 주문번호 · 고객 · 상태 · 카테고리 · 금액 · 주문일.

주문 상태는 네 가지다: `pending`(접수) · `shipped`(발송) · `delivered`(배송완료) ·
`cancelled`(취소). **네 상태는 서로 배타적이다** — 한 주문은 정확히 하나의 상태만 갖는다.

## 2. 조회 조건 (필터)

### 2-1. 상태 필터

담당자가 상태 하나를 고르면 **그 상태인 주문만** 목록에 나온다.

- `shipped`를 고르면 **발송 상태인 주문만** 보인다. 배송완료(`delivered`)된 주문은
  이미 발송을 거쳤더라도 **지금 상태가 아니므로 나오면 안 된다.**
- 상태를 고르지 않으면(전체) 모든 주문이 나온다.

> 이 규칙이 중요한 이유: 담당자는 "지금 발송 처리해야 할 건"을 보려고 이 필터를
> 쓴다. 이미 배송된 주문이 섞이면 업무 판단이 틀어진다.

### 2-2. 주문일 범위 필터

시작일과 종료일을 넣으면 **그 기간에 주문된 건**이 나온다.

- **시작일과 종료일은 둘 다 포함한다.** 6월 1일 ~ 6월 30일로 조회하면
  **6월 30일에 들어온 주문도 반드시 포함**된다.
- 한쪽만 넣으면 그쪽 방향으로만 제한한다(시작일만 = 그날 이후 전부).

> 이 규칙이 중요한 이유: 월말 마감 때 "6월 한 달"을 조회하는데 30일 주문이
> 빠지면 매출 집계가 어긋난다. 경계일 포함은 담당자의 상식적 기대다.

### 2-3. 고객 검색

고객명을 입력하면 **그 글자가 이름에 들어간 고객의 주문**이 나온다(부분 일치).
예: "김"으로 검색하면 김철수·김영희 주문이 모두 나온다.

### 2-4. 카테고리 필터

카테고리 하나를 고르면 **그 카테고리 주문만** 나온다.

### 2-5. 조건 조합

여러 조건을 함께 걸면 **모든 조건을 동시에 만족하는 주문만** 나온다(AND).
예: 카테고리=전자기기 + 상태=delivered → 전자기기이면서 배송완료인 주문만.

## 3. 조회 결과 표시

### 3-1. 건수 표기

화면에 **조회된 주문의 총 건수**를 보여준다. 이 숫자는 **실제 조회 결과 건수와
반드시 같아야 한다.**

### 3-2. 페이지 나누기

결과가 많으면 여러 페이지로 나눠 보여주고 '이전/다음'으로 이동한다.
**모든 페이지를 합치면 조회 조건에 맞는 전체 주문이 빠짐없이 나와야 한다.**
건수 표기는 현재 페이지가 아니라 **전체 건수**를 뜻한다.

### 3-3. 금액 표기

금액은 천 단위 구분 기호를 넣어 읽기 쉽게 표시한다(예: 1,234,000).
표기 형식이 달라도 **값 자체는 저장된 금액과 같아야 한다.**

## 4. 부가 기능

### 4-1. 요약 보기

'요약 보기'를 누르면 **현재 조회 결과의 금액 합계**가 화면에 나타난다.
누르기 전에는 보이지 않는다.

### 4-2. 조회 조건의 주소 반영

필터를 적용하면 **적용한 조건이 주소(URL)에 남는다.** 담당자가 그 주소를 복사해
동료에게 보내면 동료도 같은 조회 결과를 본다.

### 4-3. 초기화

'초기화'를 누르면 모든 조건이 지워지고 전체 목록으로 돌아간다.

### 4-4. CSV 내려받기

현재 조회 조건 그대로 결과를 CSV 파일로 내려받는다.

## 5. 화면 품질 기준

### 5-1. 오류 없는 화면

정상 사용 중에 **브라우저 콘솔 오류나 서버 오류(4xx·5xx)가 발생하지 않아야 한다.**
담당자에게 보이지 않더라도 오류는 기능이 깨졌다는 신호다.

### 5-2. 작은 화면 대응

**휴대폰·태블릿 폭에서도 화면이 옆으로 넘치지 않아야 한다.** 표가 넓으면 표
안에서만 좌우로 밀리고, 페이지 전체가 가로로 스크롤되면 안 된다.

### 5-3. 살아 있는 링크

화면의 모든 이동 링크는 **실제로 존재하는 페이지로 연결되어야 한다.**
없는 주소를 가리키는 링크가 있으면 안 된다.

### 5-4. 응답 속도

메인 화면은 **2초 안에** 로딩이 끝나야 한다.

### 5-5. 내부용 표시 노출 금지

개발·디버그용 안내나 배너는 **일반 사용자 화면에 나오면 안 된다.**

## 6. 이 화면이 하지 않는 일

- 주문 생성·수정·삭제는 이 화면의 기능이 아니다(별도 화면).
- 다른 사람의 권한을 바꾸거나 결제를 실행하지 않는다.

*이 문서가 바뀌면 테스트 기대값도 함께 바뀌어야 한다. 반대로 구현이 바뀌었다고
이 문서를 고치면 안 된다 — 그것은 버그를 정답으로 만드는 일이다.*
