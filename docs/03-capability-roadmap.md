# 능력 확장 설계 — 엔진이 못 하는 동작을 없애는 순서

> 작성 2026-08-08 · 기준 코드 `66a729b`
>
> **진행 상황: A·B·C·D·E 구현 완료 (2026-08-08). 다음은 F(TOTP·메일 인증).**
> 설계와 달라진 점 하나 — 초기화 훅은 `write_checks.reset`이 아니라 최상위
> `write_reset`이다. `write_checks`가 목록이라 그 안에 키를 둘 수 없었다.
>
> 이 문서는 "테스트 케이스가 부족하다"가 아니라 **엔진 자체가 못 하는 동작**을
> 다룬다. 현재 스텝 DSL은 `goto/click/fill/select/check/press/wait_for/wait_ms`
> 와 단언 5종이 전부다. 오픈소스 3종 실측(Gitea·Kanboard·Django)은 이 범위
> 안에서 됐지만, 주문·결제형 흐름과 첨부·팝업이 있는 화면은 이 범위 밖이다.

## 지키면서 간다 (설계 원칙)

1. **판정 결정성.** 같은 입력이면 같은 결과. LLM은 판정에 끼지 않는다.
   표현력을 늘리더라도 "실행마다 다른 길을 타는 테스트"는 만들지 않는다.
2. **안전 경계는 좁히지 않는다.** 쓰기는 승인 경로(`write_checks` +
   `--allow-write-checks`)로만. 하드블록 목록은 축소 금지. 새로 생기는 도달
   범위(iframe·팝업·업로드)에도 **같은 검사를 그대로 적용**한다.
3. **비밀은 새 기능에서도 비밀.** 추출한 변수, TOTP 비밀키처럼 새로 생기는
   값도 기존 마스킹 규칙(`***`)의 대상이다.
4. **만든 능력은 Lab에서 실측으로 증명한다.** 기능마다 시험장에 버그를 심어
   탐지되는 것까지 확인해야 완료다.

## 전체 그림 — 7개 단위, 4단계

| 단계 | 단위 | 얻는 것 | 상태 |
|---|---|---|---|
| 1. 연결 | **A** 값 추출·변수 | 화면의 주문번호를 뽑아 다음 단계·DB 대조에 씀 | ✅ 완료 |
| 1. 연결 | **B** 실행 간 초기화 | 쓰기 검증을 반복 가능하게 — 주문 흐름 QA의 전제 | ✅ 완료 |
| 2. 도달 | **C** iframe·팝업·새 탭 | 결제창·주소검색·소셜 로그인 창에 손이 닿음 | ✅ 완료 |
| 2. 도달 | **D** 동작 4종 | 업로드·호버·드래그·스크롤 | ✅ 완료 |
| 3. 표현·인증 | **E** 반복(foreach) | "목록의 각 항목마다 같은 검사" | ✅ 완료 |
| 3. 표현·인증 | **F** TOTP·메일 인증 | 2단계 인증 로그인, 인증메일 확인 | 다음 |
| 4. 운영 | **G** 이력 축적 | 직전 1회 비교 → 최근 N회 추이 | 대기 |

1단계가 끝나면 "장바구니 담기 → 주문 → **화면의 주문번호로** DB에서 그 주문
확인"이 된다. 2단계가 끝나면 모의 결제창까지 검증 범위에 들어온다.

---

## 단위 A — 값 추출과 변수

**문제.** 화면에 뜬 값(주문번호, 발급된 코드)을 다음 스텝이나 정답 SQL에서
쓸 수 없다. 그래서 쓰기 검증이 "건수가 1 늘었나"(`expect_delta`)까지만 간다.
어느 행이 생겼는지는 못 본다.

**설계.**

```yaml
steps:
  - {action: click, selector: "#place-order"}
  - {action: wait_for, selector: "#order-no"}
  - {action: extract, selector: "#order-no", store_as: order_no,
     pattern: "([0-9]{8,})"}          # 선택: 정규식 1그룹만 취함
  - {action: goto, value: "/orders/{{order_no}}"}
  - {action: assert_text, selector: "h1", value: "{{order_no}}"}
query:
  db: sqlite:///staging.db
  sql: "SELECT status FROM orders WHERE order_no = :order_no"
  params: {order_no: "{{order_no}}"}
```

- **두 가지 치환을 구분한다.** `${이름}`은 지금처럼 설정을 읽는 시점의
  환경변수(비밀 주입용). `{{이름}}`은 실행 중 추출한 값. 문법을 나눠야
  "비밀번호를 화면에서 추출해 SQL에 끼워넣는" 식의 혼동이 안 생긴다.
- **SQL은 문자열로 끼워넣지 않는다.** `{{var}}`를 SQL 본문에 쓰는 것은
  금지하고, `params`를 통한 **바인딩만** 허용한다. 추출값이 SQL 조각이어도
  데이터로만 취급되게 하기 위해서다(주입 차단).
- **범위는 한 시나리오 안.** 시나리오끼리 값을 넘기면 실행 순서에 의존이
  생겨 병렬성과 독립성이 깨진다. 흐름은 한 시나리오에 이어 쓴다.
- **실패 규칙.** 요소 없음, 패턴 불일치, 빈 값 → 그 시나리오 실패. 추출값은
  리포트에 남기되 secret 판정에 걸리면 `***`.

**Lab 채점.** Commerce Lab에 "주문 상세의 주문번호를 추출해 seed와 대조"
케이스 추가. 2^53 초과 주문번호 버그(SHOP-B05)와 결합하면 추출 경로의 큰
정수 정확도까지 같이 채점된다.

## 단위 B — 실행 간 데이터 초기화

**문제.** 주문을 넣으면 데이터가 남는다. 다음 실행의 "13건" 검사가 거짓으로
깨지므로, 초기화 없이는 쓰기 검증을 반복할 수 없다. 현재 쓰기 검증이 실전
미검증인 이유가 이것이다.

**설계.**

```yaml
write_checks:
  reset:                                  # 실행 시작 시 1회
    http: {method: POST, url: "/__test__/reset",
           headers: {Authorization: "Bearer ${RESET_TOKEN}"}}
    # 또는  command: "python seed.py"     # YAML 폴더 기준 상대 실행
```

- reset은 데이터를 지우는 동작이므로 **`--allow-write-checks` 없이는 절대
  실행하지 않는다.** 승인 없는 실행에서는 reset 정의가 있어도 건너뛰고
  쓰기 시나리오 전체를 기존처럼 차단한다.
- **reset 실패는 `infra_error`(종료코드 2).** 초기화가 안 된 상태로 판정을
  내리지 않는다.
- 수행 여부·대상을 리포트에 기록한다.

**Lab 채점.** HANDOFF에 예고해 둔 Commerce "중복 제출" 버그를 이 단위에서
심는다. Lab에는 이미 `LAB_CONTROL_TOKEN` 기반 reset/seed 엔드포인트가 있어
Lab 쪽 추가 작업이 작다.

## 단위 C — iframe·팝업·새 탭

**문제.** 결제창(PG)·주소검색(우편번호)·소셜 로그인은 iframe이나 별도 창으로
뜬다. 지금은 이 안의 요소에 도달할 방법이 없다.

**설계.**

```yaml
steps:
  - {action: click, selector: "#pay"}
  - {action: wait_popup}                                   # 새 창으로 전환
  - {action: fill, selector: "#card", value: "${TEST_CARD}",
     frame: "iframe#pg-form"}                              # 창 안의 iframe
  - {action: click, selector: "#confirm", frame: "iframe#pg-form"}
  - {action: close_popup}                                  # 원래 창으로 복귀
```

- 스텝에 `frame` 필드를 추가한다. 중첩 iframe은 `"iframe#a >> iframe#b"`.
- 팝업은 **페이지 스택**으로 다룬다. `wait_popup`이 새 창을 기다려 활성
  페이지를 전환하고(타임아웃 시 실패), `close_popup`이 복귀한다.
- **감시와 안전장치를 똑같이 건다.** 콘솔 오류·HTTP 실패 수집과 하드블록
  검사(`find_destructive`)는 프레임·팝업 안의 클릭에도 동일 적용. 스크린샷은
  활성 페이지 기준으로 찍고 절차서에 "팝업에서"를 표기한다.

**Lab 채점 — 새 시험장 Checkout Lab.** 외부 PG를 흉내 낸 **모의 결제창**을
Lab이 직접 서빙한다(외부 접속 없음). 심을 버그: 결제창 표시 금액 불일치,
결제 완료 후 주문 미생성, 중복 결제 허용. 실제 PG 연동은 계속 범위 밖이며
"PG 테스트 모드 + 테스트 카드"를 문서로 안내한다.

## 단위 D — 동작 4종

- `upload`: `set_input_files`. 값은 **YAML 폴더 기준 상대경로만** 허용.
  바깥 절대경로는 거부한다 — 시스템 파일을 대상 앱에 올려버리는 사고 방지.
- `hover`, `scroll_to`, `drag`(selector를 value 대상으로 끌어놓기).
- 전부 Playwright 기본 기능의 얇은 노출이라 크기는 작다.

## 단위 E — 반복은 넣고, 조건분기는 안 넣는다

**foreach.**

```yaml
spec_checks:
  - name: "상품카드-{{item}}"
    foreach: {var: item, in: [셔츠, 바지, 신발]}   # 또는 in_file: cases.json
    page: /products
    steps:
      - {action: assert_text, selector: ".card", value: "{{item}}"}
```

계획 단계에서 N개의 독립 시나리오로 **미리 전개**한다. 리포트에 각각 한
줄씩 남고, 병렬 실행·직전 비교도 개별로 된다.

**if/else는 넣지 않는다.** 조건분기는 "상황에 따라 통과 기준이 달라지는
테스트"를 만들고, 그런 테스트는 실패를 숨긴다. 화면 상태가 둘로 갈리는
경우라면 그것은 시나리오 두 개(각 상태를 만들어 놓고 검증)로 써야 한다.
이 결정은 원칙 1(결정성)의 직접 귀결이다.

## 단위 F — 인증 확장

- **TOTP(2단계 인증 6자리).** `value: "${TOTP:MY_2FA_SECRET}"` — 환경변수의
  비밀키로 표준(RFC 6238) 코드를 실행 시점에 생성한다. 표준 라이브러리로
  구현 가능해 의존성 추가가 없고, 비밀키·생성 코드 모두 마스킹한다.
- **메일 인증.** Mailpit/MailHog 같은 **테스트 메일함**의 API를 정답원으로
  대조하고, 인증 링크를 추출해 방문한다(단위 A의 추출·변수에 의존).
  운영 메일함은 대상이 아니다.
- **명시적 범위 밖.** CAPTCHA 우회는 만들지 않는다 — 봇을 막으려는 장치를
  뚫는 기능은 이 도구의 목적과 반대다. 스테이징에서 CAPTCHA를 끄거나 테스트
  우회 키를 받는 것이 올바른 경로다. 실제 소셜 로그인(카카오·구글)은 테스트
  대역(가짜 IdP)을 권장하고 실계정 자동 로그인은 지원하지 않는다.

## 단위 G — 이력 축적

지금은 직전 실행 1회와만 비교한다(`history.py`). 로컬 우선으로 확장한다:
`webtest-agent history` 명령이 `runs/`를 훑어 시나리오×실행 추이 표(JSON·
텍스트)를 만들고, `report.html`에 최근 N회 미니 추이를 넣는다. **서버 축적
(Console 연동)은 보관·삭제 정책과 권한을 정한 뒤 별도 단위로 진행한다** —
site 저장소의 기존 원칙 그대로다.

## 명시적으로 만들지 않는 것

- CAPTCHA 우회, 실카드·운영 결제, 운영망 쓰기 기본 차단 완화
- 판정에 LLM 개입
- 시나리오 간 변수 전달(독립성 파괴), 스텝 if/else(결정성 파괴)

## 완료 기준 (모든 단위 공통)

1. 단위 테스트 추가
2. 데모앱 또는 Lab 실측 (탐지까지 확인)
3. 문서 갱신 (README·QUICKSTART·USER_GUIDE 해당 부분)
4. Lab 계약이 바뀌면 기준선 재측정

순서는 A → B → (C ‖ D) → E → F → G. A·B가 끝나는 시점에 "주문 → 주문번호로
DB 확인"이 실증 가능해지고, 그것이 이 로드맵의 첫 번째 이정표다.
