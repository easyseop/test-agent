# webtest-agent 쉬운 사용 가이드

> 개발자가 아니어도 테스트 준비, 실행 요청, 결과 확인을 할 수 있도록 설명한 문서입니다.

## 1. 이 도구는 무엇을 하나요?

webtest-agent는 사람이 웹사이트를 확인하듯 화면을 열고 버튼을 누르며,
다음 항목을 자동으로 점검합니다.

- 페이지와 버튼이 열리는지
- 로그인과 권한이 정상인지
- 검색·필터 결과가 맞는지
- 화면의 데이터가 API나 데이터베이스와 일치하는지
- 긴 주문번호나 ID가 반올림되지 않고 정확히 일치하는지
- 저장 전후 데이터가 의도한 만큼 변했는지
- 콘솔 오류나 서버 오류가 발생했는지
- 첫 화면을 여는 순간 발생한 오류가 있는지
- 화면이 이전 기준 화면과 달라졌는지

실행이 끝나면 스크린샷이 들어간 HTML 리포트, 단계별 절차서, 영상,
Playwright Trace를 남깁니다.

## 2. 결과는 세 가지로 구분합니다

| 표시 | 의미 | 다음 행동 |
|---|---|---|
| 통과 | 실제 테스트를 실행했고 기대 결과와 일치함 | 결과를 보관하거나 다음 단계 진행 |
| 실패 | 테스트를 실행했지만 기능·데이터가 기대와 다름 | 실패 상세와 증거 확인 |
| 실행 불가 | 사이트 접속, 로그인, 설정 또는 테스트 정의 문제로 판정하지 못함 | 원인을 해결한 뒤 다시 실행 |

**실행 불가는 통과가 아닙니다.** 사이트가 꺼져 있거나 실행할 테스트가
하나도 없으면 `report.html`에 실행 불가 사유가 표시되고 명령도 오류로 끝납니다.
전체 제한 시간을 넘겨 일부 테스트만 끝난 경우도 실행 불가입니다.

## 3. 시작 전에 준비할 것

실제 앱을 테스트하려면 담당자에게 다음 항목을 받으세요.

- 테스트용 또는 스테이징 사이트 주소
- 테스트 계정과 역할(일반 사용자, 관리자 등)
- 테스트할 기능 설명서 또는 업무 규칙
- 매번 되돌릴 수 있는 테스트 데이터
- 데이터 대조가 필요하면 읽기 전용 DB 주소 또는 검증 API
- 저장·수정 테스트를 허용하는지에 대한 명시적 확인

비밀번호, 쿠키, DB 비밀번호는 YAML 파일에 직접 쓰지 않습니다. 환경변수로
전달합니다.

## 4. 가장 쉬운 체험 방법

처음에는 함께 제공되는 주문 관리 데모로 확인하세요.

### 설치

**준비물: Python 3.11 이상.** 먼저 버전부터 확인합니다.

```bash
python3 --version
```

`Python 3.11.x` 이상이 나와야 합니다. 낮은 숫자(예: 3.9)가 나오면 먼저
Python을 새로 설치하세요. 이걸 건너뛰면 다음 단계에서 `setup.py 없음`처럼
**원인과 상관없어 보이는 오류**가 나서 한참 헤매게 됩니다.

그다음 도구를 내려받습니다. 원하는 폴더에서 아래를 실행하면 `test-agent`
폴더가 생기고, 그 안으로 들어갑니다.

```bash
git clone https://github.com/easyseop/test-agent
cd test-agent
```

이제 아래를 순서대로 한 번 실행합니다.

```bash
python3 -m venv .venv         # 이 프로젝트 전용 공간을 만듭니다
. .venv/bin/activate          # 그 공간으로 들어갑니다 (Windows: .venv\Scripts\activate)
pip install -e ".[db,dev]" -c constraints.txt
python -m playwright install chromium
```

> 두 번째 줄(`activate`)은 **터미널을 새로 열 때마다** 다시 실행해야 합니다.
> 안 하면 "명령을 찾을 수 없다"는 오류가 납니다.

### 정상 기능 확인

```bash
./scripts/run_demo.sh
```

기본은 읽기 전용입니다. 정상이라면 **실패 0건**으로 끝나고, 저장·삭제 등
위험 동작 4개가 “안전 차단 목록”에 표시됩니다. (통과 개수는 검사 항목이
늘어나면 함께 늘어나므로, 개수가 아니라 실패 0건을 기준으로 보세요.)

시드 DB의 주문 등록 테스트까지 실행하려면 다음처럼 명시적으로 승인합니다.

```bash
./scripts/run_demo.sh --write
```

### 일부러 넣은 버그 찾기

```bash
./scripts/run_demo.sh --bug
```

이 모드는 실패가 나와야 정상입니다. 상태 필터, 날짜 경계, 잘못된 버튼 코드 등
미리 심어 둔 버그를 찾아내는 시연입니다. 명령이 종료코드 1로 끝나는 것도
“버그를 검출했다”는 뜻이므로 이 체험에서는 정상입니다.

### 로그인 기능 확인

```bash
./scripts/run_demo.sh --auth
```

로그인 세션 재사용과 화면 개인정보 마스킹을 확인합니다.

## 5. 결과 확인 방법

실행이 끝나면 화면에 `runs/날짜-시간/` 형태의 폴더가 표시됩니다.

1. `report.html`을 더블클릭합니다.
2. 맨 위의 실행 상태가 통과, 실패, 실행 불가 중 무엇인지 확인합니다.
3. 실패가 있으면 실패한 시나리오 이름과 첫 번째 사유를 봅니다.
4. 각 단계의 스크린샷을 확인합니다.
5. 더 자세한 재현 과정이 필요하면 `walkthrough.md`를 봅니다.

주요 파일:

| 파일 | 언제 사용하나요? |
|---|---|
| `report.html` | 가장 먼저 보는 공유용 결과 |
| `walkthrough.md` | 사람이 따라 할 수 있는 기능 절차·버그 재현 |
| `report.json` | 다른 시스템이나 AI가 결과를 읽을 때 |
| `videos/` | 전체 화면 흐름을 확인할 때 |
| `traces/` | 개발자가 DOM·네트워크·콘솔을 정밀 분석할 때 |

## 6. 실제 사이트 테스트를 요청하는 방법

비개발자가 선택자나 SQL을 직접 작성할 필요는 없습니다. 앱 설명서, 테스트 URL,
소스 경로를 준비한 뒤 Codex나 Claude에 다음처럼 요청하세요.

```text
이 웹앱의 테스트 설정을 만들어줘.

- 테스트 URL: <스테이징 URL>
- 앱 설명서: <문서 경로>
- 앱 소스: <소스 경로>
- 테스트 계정 역할: <일반 사용자/관리자>
- 허용된 쓰기 동작: <없음 또는 구체적인 항목>

먼저 discover를 실행해 화면 요소를 확인하고,
설명서를 기대값의 근거로 사용해 YAML 초안을 만들어줘.
삭제·결제·메일 발송은 승인 없이 실행하지 말고,
생성된 테스트의 목적과 합격 기준을 비개발자도 이해할 수 있게 설명해줘.
```

초안이 만들어지면 다음 세 가지만 확인하면 됩니다.

1. 테스트 이름과 설명이 실제 업무를 맞게 표현하는가?
2. “무엇이 나오면 통과인가?”가 맞는가?
3. 저장·삭제·발송 같은 위험 동작을 실행해도 되는가?

### 누가 무엇을 하나요?

| 담당 | 하는 일 |
|---|---|
| 사용자·업무 담당자 | 정상 기준과 위험 동작 범위 확인 |
| Codex·Claude | 화면을 조사하고 테스트 YAML 작성 |
| Runner | 로그인·클릭·검증·리포트 생성 |
| 개발자 | 발견된 실제 버그 수정 |

### 한 번 만든 테스트는 어디에 남기나요?

| 저장 위치 | 내용 |
|---|---|
| `docs/TEST_PLAN.md` | 사람이 읽는 목적과 합격 기준 |
| `configs/<사이트>.yaml` | Runner가 반복 실행할 테스트 |
| `runs/` | 실행할 때마다 생기는 결과와 증거 |

테스트는 배포 전, 관련 코드 변경 후, 정기 점검 때 다시 실행합니다.
LLM 위키는 테스트가 많아진 뒤 검색·정리용으로 추가하며, 지금은 필수가 아닙니다.

## 7. 안전 수칙

- 운영 사이트보다 테스트·스테이징 환경을 사용합니다.
- 운영 DB는 읽기 전용 계정으로 조회만 합니다.
- SQL 정답원은 단일 `SELECT` 또는 `WITH` 조회만 실행됩니다. Runner가
  쓰기·관리 문장과 여러 문장을 차단하지만, DB 계정도 반드시 읽기 전용이어야 합니다.
- 로그인 상태 파일은 실행 후 자동 삭제됩니다. 꼭 보관해야 할 때만
  `--preserve-auth-state`를 사용하고, 비밀번호처럼 취급해 공유하지 않습니다.
- 삭제, 결제, 초대, 이메일·문자 발송은 기본적으로 실행하지 않습니다.
- 자동 탐색은 저장·수정도 클릭하지 않으며, 이 최소 차단 목록은 설정에서 제거할 수 없습니다.
- YAML의 쓰기 테스트는 시드·스테이징임을 확인한 뒤 `--allow-write-checks`로 승인해야 실행됩니다.
- 저장 테스트는 매번 초기화할 수 있는 시드 데이터에서만 실행합니다.
- 리포트의 영상과 Trace에는 개인정보가 남을 수 있으므로 공유 범위를 확인합니다.
- 기준 화면 갱신은 실제 UI 변경이 승인됐을 때만 수행합니다.

## 8. 자주 생기는 문제

| 화면에 보이는 내용 | 뜻 | 해결 방법 |
|---|---|---|
| 대상 앱에 접속할 수 없습니다 | 사이트가 꺼져 있거나 주소·네트워크가 잘못됨 | 브라우저에서 URL을 직접 열고 담당자에게 상태 확인 |
| 실행할 테스트 시나리오가 0개입니다 | 테스트 정의가 없고 자동 탐색도 꺼져 있음 | YAML에 테스트를 추가하거나 crawl/button_sweep 활성화 |
| 크롤링한 페이지가 0개입니다 | 로그인, 제외 패턴, 첫 화면 로딩 문제 | 계정과 `crawl.exclude_patterns` 확인 |
| 인증 실패 | 계정·비밀번호·로그인 성공 조건 문제 | 환경변수와 로그인 절차 확인 |
| 인증 상태 파일 삭제 경고 | 파일 권한이나 다른 프로그램 사용으로 자동 삭제 실패 | 파일을 공유하지 말고 직접 삭제 |
| 안전 차단 목록 | Runner가 쓰기·발송·세션 변경을 실행하지 않고 건너뜀 | 조회 테스트라면 정상. 허용된 쓰기 검증만 별도 승인 |
| UI↔DB 불일치 | 화면과 정답 데이터가 다름 | 리포트의 누락·초과 행을 개발자에게 전달 |
| 조회 SQL 안전 차단 | SQL에 쓰기·관리 키워드 또는 여러 문장이 포함됨 | 단일 `SELECT/WITH` 조회로 바꾸고 DB 계정의 read-only 권한 확인 |
| 긴 ID 한 자리 불일치 | 화면·API·DB 중 한 곳에서 큰 숫자가 반올림되거나 잘림 | ID를 문자열로 전달하는지 개발자에게 확인 요청 |
| 첫 화면 로드 오류 | 화면은 보여도 시작 중 콘솔·페이지·HTTP 오류가 발생 | 리포트의 첫 오류를 개발자에게 전달. 합의된 리소스 404만 URL 패턴으로 제외 |
| 전체 실행 제한 시간 초과 | 정해진 시간 안에 모든 테스트를 마치지 못함 | 완료 수를 확인하고 느린 단계·대상 상태를 고친 뒤 전체 재실행 |
| 무반응 경고 | 클릭 뒤 관찰할 수 있는 변화가 없음 | 실제 죽은 버튼인지 업무 담당자가 확인 |

## 9. 용어를 쉽게 설명하면

- **시나리오:** 사람이 따라 하는 한 개의 테스트 절차
- **스텝:** 시나리오 안의 클릭, 입력, 확인 한 단계
- **기대값:** 무엇이 나오면 통과인지 정한 기준
- **오라클:** DB·API·업무 설명서처럼 기대값의 근거가 되는 자료
- **회귀 테스트:** 예전에 되던 기능이 지금도 되는지 반복 확인
- **Trace:** 개발자가 실패 순간의 화면·DOM·네트워크를 되돌려 보는 기록
- **시드 데이터:** 테스트가 끝난 뒤 원래 상태로 다시 만들 수 있는 고정 데이터

## 10. 도움을 요청할 때 전달할 것

다음 정보를 함께 보내면 원인 확인이 빨라집니다.

- 사용한 설정 YAML 경로
- 실행한 명령
- 실행 폴더의 `report.html`과 `report.json`
- 기대했던 동작
- 실제로 본 동작

비밀번호, 인증 쿠키, 토큰, 실제 고객 데이터는 전달하지 않습니다.

## 11. 현재 Lab 확인 결과

2026-07-27 최신 로컬 Runner 작업본은 Auth Lab 정상 시나리오 7/7을 통과했고,
의도적 버그 8개 중 7개를 찾았습니다. 예상 밖 finding과 실행 불가는

업무 테스트 정의와는 별도로 Runner 자체 탐지력을 개선할 후속 항목입니다.
