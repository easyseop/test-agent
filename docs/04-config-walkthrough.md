# 설정 한 바퀴 — 아무것도 없는 상태에서 실행까지

`QUICKSTART.md`는 **무엇을 쓸 수 있는지**를 늘어놓은 사전이다. 이 문서는
**어떤 순서로 하는지**를 한 바퀴 돌린다. 아래 출력은 전부 동봉 데모앱에서
실제로 돌려 받아 적은 것이다.

**핵심은 이 배분이다.**

| 누가 | 무엇을 | 몇 번 |
|---|---|---|
| 사람 | 무엇이 맞는지 정한다 | 기능마다 한 번 |
| 도구 | 화면·응답 구조를 뽑아 준다 | 명령 한 줄 |
| LLM | 그 둘을 YAML로 옮긴다 | 설정마다 한 번 |
| 봇 | 실행하고 판정한다 | **매번, 토큰 0** |

---

## 0단계. 시작 전에 딱 하나만 준비한다

**"이건 이래야 한다"는 문장.** 기획서·설명서·업무 규칙에서 가져온다.

> 상태를 '배송중'으로 거르면 배송중인 주문만 나와야 한다.
> 시작일과 종료일은 둘 다 포함이다.

⚠️ **구현 코드에서 뽑으면 안 된다.** 코드의 조건문을 그대로 옮기면 그 코드에
들어 있는 버그까지 기대값에 복사된다. 그러면 그 검사는 **영원히 통과한다.**

> 실제 사례: 설명서에 "종료일 포함"이라 적혀 있었고 구현은 `<`를 써서 경계 3건을
> 빠뜨리고 있었다. 설명서에서 기대값을 뽑았기 때문에 잡혔다. 코드를 베꼈다면
> 못 잡았다.

코드는 **셀렉터·테이블명 같은 좌표를 확인할 때만** 본다.

---

## 1단계. 화면에 뭐가 있는지 뽑는다

최소 설정으로 시작한다. 주소 한 줄이면 된다.

```yaml
# configs/우리사이트.yaml
target:
  base_url: http://127.0.0.1:5057
```

```bash
python -m webtest_agent discover -c configs/우리사이트.yaml
```

```
페이지 3개 → runs/20260811-154748/discovery.json
  / — 버튼 4 · 링크 4 · 입력 3 · 셀렉트 2 · 표 1  (주문 관리 대시보드)
      #orders-table  123행  [주문번호 | 고객 | 상태 | 카테고리 | 금액 | 주문일]
  /about — 버튼 0 · 링크 1 · 입력 0 · 셀렉트 0 · 표 0  (소개 — 주문 관리 대시보드)
  /new — 버튼 1 · 링크 1 · 입력 3 · 셀렉트 2 · 표 0  (주문 등록 — 주문 관리 대시보드)
```

**여기서 얻는 것**: 표의 주소(`#orders-table`)와 열 이름이 그대로 나온다.
개발자도구를 열 필요가 없다.

**행 수(123행)를 같이 보는 이유**: 1행짜리 표를 정답원과 대조해봐야 증명되는 게
거의 없다. **설정을 쓰기 전에** 알아야지, 다 돌리고 리포트를 열어야 알면 늦다.

**여기서 사람이 하는 결정**: 어느 화면의 어느 표를 볼 것인가.

## 2단계. 정답원을 정한다

화면이 맞는지 판단하려면 **화면 바깥의 기준**이 필요하다. 화면을 화면과
비교하면 아무것도 증명되지 않는다.

| 붙을 수 있으면 | 쓴다 |
|---|---|
| 스테이징 DB | `query.db` + `query.sql` |
| 그 화면이 쓰는 REST API | `query.api` |

**API를 쓸 때는 응답 구조를 손으로 찾지 않는다.**

```bash
python -m webtest_agent inspect-api "/api/orders?status=shipped" -c configs/우리사이트.yaml
```

```
응답 구조 — /api/orders?status=shipped

[1] rows_path: orders   — 37개 항목
      amount                                       숫자     66800
      category                                     문자열    전자기기
      created_at                                   문자열    2026-06-20
      customer                                     문자열    이서연
      id                                           숫자     1007
      status                                       문자열    shipped

────────────────────────────────────────────────────────────
붙여넣을 설정 초안 (후보 [1] 기준):

  query:
    api:
      url: '/api/orders?status=shipped'
      rows_path: orders
      columns: [amount, category, created_at, customer]

columns는 화면 표의 열과 **같은 순서로** 맞춰야 합니다.
위 목록은 응답에 있는 필드일 뿐, 무엇을 대조할지는 정해 주세요.
```

**여기서 사람이 하는 결정**: 어느 배열이 목록인지, 어느 필드를 대조할지.
도구는 후보를 **전부** 보여줄 뿐 고르지 않는다.

## 3단계. "이건 이래야 한다"를 설정으로 옮긴다

**여기가 LLM이 할 일이다.** IDE의 AI에게 두 가지를 준다.

1. `runs/<시각>/discovery.json` (1단계 결과)
2. 0단계에서 정한 문장 몇 줄

사이트에 접속시킬 필요 없다. 뽑아둔 파일만 주면 된다.

나온 결과는 이런 모양이다.

```yaml
data_checks:
  - name: 상태필터-배송중
    description: 상태를 배송중으로 거르면 배송중 주문만 나와야 한다
    page: /
    steps:
      - {action: select, selector: "#status", value: "shipped"}
      - {action: click, selector: "#apply"}
      - {action: wait_for, selector: "#orders-table"}
    ui_table:
      selector: "#orders-table"
      columns: [주문번호, 고객, 상태, 금액]
    query:
      api:
        url: "/api/orders?status=shipped"
        rows_path: orders
        columns: [id, customer, status, amount]
```

⚠️ **LLM이 쓴 기대값을 그대로 믿지 않는다.** LLM에게 준 것은 *화면 구조*와
*문장*이다. 문장이 틀렸으면 설정도 틀린다. **문장이 맞는지는 사람이 본다.**

## 4단계. 돌리기 전에 셀렉터를 확인한다

```bash
python -m webtest_agent check-config -c configs/우리사이트.yaml
```

```
✓ [data_check] 상태필터-배송중
     참고            헤더 6개 · 37행   주문번호 | 고객 | 상태 | 카테고리 | 금액 | 주문일

────────────────────────────────────────────────────────────
시나리오 1개 · 못 찾음 0개 · 확인 못 함 0개
셀렉터는 전부 찾았습니다. 이 명령은 셀렉터가 있는지만 봅니다 — 기대값이 맞는지는
보지 않습니다.
```

틀린 데가 있으면 이렇게 나온다.

```
✗ [data_check] 상태필터-배송중  — 못 찾음 1개
     못 찾음    1. select  #상태
     확인 못 함  2. click  #apply   1개
     확인 못 함  3. wait_for  #orders-table   1개
     확인 못 함  표  #orders-table   1개

────────────────────────────────────────────────────────────
시나리오 1개 · 못 찾음 1개 · 확인 못 함 3개
```

**'못 찾음'과 '확인 못 함'은 다르다.**

- **못 찾음** — 앞이 다 성공한 상태에서 0개. **이것부터 고친다.**
- **확인 못 함** — 앞이 막혀서 화면이 원래 상태가 아니다. 틀렸다는 뜻도,
  맞다는 뜻도 아니다.

앞의 '못 찾음'을 고치고 다시 돌리면 뒤가 저절로 풀리는 경우가 대부분이다.

## 5단계. 실행한다

```bash
python -m webtest_agent run -c configs/우리사이트.yaml
```

```
실행 완료: 통과 8 · 경고 0 · 실패 0 (총 8, 15.7s)
데이터 대조: 1건 · 화면 37행 / 정답원 37행
스윕 커버리지: 발견 11개 중 7개 클릭 검사 (안전차단 4)
리포트: runs/20260811-154827/report.html (스크린샷 내장 단일 파일)
```

> **내가 적은 건 1개인데 8개가 돌았다?** 맞다. 나머지 7개는 **스윕**이다 —
> 크롤링으로 찾은 버튼·링크를 눌러 보고 오류가 나는지 본다. 내가 적지 않은
> 화면까지 훑어 주는 셈이다.
>
> `스윕 커버리지` 줄이 **무엇을 안 눌렀는지**까지 알려준다. 위 실행에서는
> 11개 중 4개를 누르지 않았는데, 삭제·결제처럼 되돌릴 수 없어 보이는 동작을
> 승인 없이 누르지 않기 때문이다. **안 한 것을 안 했다고 말하는 것**이 요점이다.
>
> 필요 없으면 `button_sweep.enabled: false`로 끄거나, 크롤링 자체를
> `crawl.enabled: false`로 끈다.

**결과는 세 가지로만 갈린다.**

| 종료코드 | 뜻 | 해야 할 일 |
|---:|---|---|
| 0 | 전부 판정했고 전부 통과 | 없음 |
| 1 | **제품 결함** 있음 | 코드를 본다 |
| 2 | **판정 불가** — 결함은 없는데 확인을 못 했다 | 환경을 본다(DB·API·접속) |

**2를 0으로 착각하면 안 된다.** "테스트가 안 돌았는데 통과"가 이 시스템에서
제일 위험한 사고다.

`report.json`의 `summary.not_proven`이 그중 몇 건이 판정 불가인지 알려준다
(실패 건수 안에 포함된 숫자다).

## 언제 무엇을 더 붙이나

처음부터 다 쓸 필요 없다. **필요한 상황이 왔을 때** 그 줄만 추가한다.

| 이런 상황이면 | 이것을 쓴다 |
|---|---|
| 한글을 타이핑하는 화면이다 | `type_ime` — `fill`은 조합을 안 만들어 조합 중 결함을 못 잡는다 |
| 값이 **정확히** 그것이어야 한다 | `assert_text_exact` — `assert_text`는 부분 일치라 오염된 값도 통과한다 |
| 저장·등록이 실제로 됐는지 봐야 한다 | `write_checks` + `expect[]` — 건수 하나만 보면 증명되는 게 거의 없다 |
| 실제 개인정보가 화면에 있다 | `report.mask_patterns` — 캡처만 가리면 리포트 본문에 남는다 |
| 무해한 경고가 실패를 만든다 | `target.ignore_console_patterns` — 무시한 건 리포트에 기록된다 |
| 로그인이 시나리오마다 풀린다 | `auth.per_context: true` |
| 화면 글자가 정답원과 다르다 | `target.locale`을 맞춘다. 안 되면 `ui_table.value_map` |

문법은 `QUICKSTART.md` §2-2에 전부 있다.

## 사람이 반드시 해야 하는 두 가지

나머지는 도구나 LLM이 초안을 낼 수 있다. 이 둘은 안 된다.

**① 무엇이 맞는지 정하는 것 (기대값)**
구현을 보고 베끼면 버그가 기대값에 복제되어 영원히 검출되지 않는다.
이건 자동화의 문제가 아니라 **그렇게 하면 테스트가 무의미해지는** 문제다.

**② 무엇을 가리고 무엇을 무시할지 승인하는 것**
`mask_patterns`와 `ignore_console_patterns`는 둘 다 **덮는** 행위다.
자동으로 넓히면 진짜 결함까지 조용히 가려진다. 그래서 무시한 것은 리포트에
건수로 남고, 지운 것이 아니라 **뺀 것**임이 드러나게 되어 있다.

---

## 설정이 조용히 약해지는 것을 막는 장치

리포트에는 `checks_sha256`(검사 내용 지문)이 박힌다. 대조할 열을 줄이거나
사후조건을 지우면 **출력이 똑같아 보여도** 이 값이 달라진다. 직전 실행과 다르면
리포트에 이렇게 뜬다.

> ⚠️ 검사 정의가 직전 실행과 다릅니다 — 같은 조건의 비교가 아닙니다

주석이나 제목만 고쳤을 때는 바뀌지 않는다. **검사 내용만** 본다.
